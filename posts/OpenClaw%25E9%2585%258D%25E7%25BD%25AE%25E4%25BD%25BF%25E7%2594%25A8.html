信息

由于 OpenClaw 更新频繁，个别界面名称、渠道配置项和命令细节可能会随版本变化，实际操作时建议同时对照官方文档。

先说结论：进阶不是“装更多插件”，而是把它变成一个能长期工作的系统 ​

我觉得很多人第一次装完 OpenClaw 后，都会有一种错觉：界面能打开、模型能回复，好像就算搭好了。

但真正开始用以后，很快会遇到几个瓶颈：

  • 默认权限太保守，导致它只能聊天
  • 原生搜索依赖外部 Key，没有额外配置就直接失效
  • 工作区文件不理解，行为跑偏也不知道该改哪里
  • 接入聊天渠道后，只能被动回复，不能主动工作
  • 所有记忆和设定都堆在一个机器人里，后面越来越乱

所以在我看来，进阶配置使用 OpenClaw ，本质上不是“会不会点安装按钮”，而是你有没有把 OpenClaw 当成一个可配置、可扩展、可长期运行的代理系统来使用。

第一步：安装完先改默认工作模式，不然它几乎干不了活 ​

我自己最想先强调的一点就是：刚安装好的 OpenClaw，默认更像是一个“会聊天的模型外壳”，而不是一个“能调用工具的代理”。

如果这个状态不改，后面你会遇到一种典型体验：

  • 它会解释很多
  • 它会道歉很多
  • 但它真正调用工具、执行步骤、读配置、改文件的能力很弱

所以安装完成之后，第一件事不是去试各种花哨玩法，而是先进入配置页，把默认偏 messaging 的工作模式调整成更适合执行任务的模式，让它真正具备调用工具的权限。

json
"tools": {
  "profile": "messaging",  
  "profile": "full",  
},

把这一步放在最前面，原因也很直接：

不先放开工具权限，后面的搜索、自动化、渠道接入、多 Agent，几乎都只会停留在“它知道怎么做”，而不是“它真的去做”。

第二步：先读懂 workspace，你才能真正调教 OpenClaw ​

整篇内容里，最重要的部分不是某个单独的 Skill，而是把 OpenClaw 的工作区文件讲清楚了。

很多人把 OpenClaw 当黑盒来用，结果一旦行为不符合预期，就只能反复重启、重装、换模型。其实更高效的办法，是先知道它的行为主要受哪些文件控制。

先盯住下面这几个文件，位于 ~/.openclaw/workspace：

  • AGNETS.md：工作规范，决定它应该怎么做事
  • IDENTITY.md & SOUL.md：自我定位，决定它“觉得自己是谁”
  • USER.md：用户画像，决定它“认为你是谁”
  • TOOLS.md：工具使用规则，决定它遇到什么场景该优先用什么能力
  • MEMORY.md：长期记忆
  • memory/：按时间组织的短期记忆
  • HEARTBEAT.md：心跳机制每次执行时要遵循的指令

这套结构很重要，因为它意味着：OpenClaw 的很多行为问题，本质上不是“模型不聪明”，而是“规则没写清楚”。

比如下面这些情况：

  • 搜索时总走错工具
  • 回答风格不稳定
  • 记不住你交代过的偏好
  • 主动推送逻辑不符合你的预期

这些问题，很多时候都不是去换模型解决，而是回到 workspace 里把对应规则改清楚。

所以如果你想把 OpenClaw 用稳，我很建议先养成一个习惯： 遇到行为偏差时，优先检查 workspace，而不是先怀疑“是不是这个模型太笨了”。

第三步：默认搜索不好用，最实用的办法是直接用 Skill 重构 ​

我觉得大多数人迟早都会撞上的一个典型问题是：新装的 OpenClaw 在执行联网搜索时，调用默认搜索工具后直接报错：

txt
missing_brave_api_key

这个报错背后其实说明了两件事：

  1. 它的原生搜索链路依赖额外(brave)的 API Key。
  2. 默认链路一旦缺一环，就会立刻失效。

既然默认搜索不好用，那就直接用 Skill 把它替换掉。

用 Tavily Web Search 修主搜索 ​

我会优先装的第一个搜索 Skill，就是 Tavily Web Search。

它的思路很适合当主搜索方案：

  • 能直接补上联网搜索能力
  • API Key 相对更容易获取
  • 搜索结果质量也比较稳定

但这里有个很多人会忽略的重点： 装完 Skill 还不够，你还要同步做两件事：

  1. 在 openclaw.json 里把默认搜索关掉
json
"tools": {
  "profile": 'full',
  "web": {  
    "search" : {  
        "enabled" :false
    } 
  }  
},
  1. 在 TOOLS.md 里明确告诉它：网络搜索优先走 Tavily
TOOLS.md
markdown
## Web Search
Use the openclaw-tavily-search skill as the top-priority search tool when do web search.

这一点非常关键。因为如果你只装 Skill，不改工具规则，它仍然可能继续尝试走原来的默认搜索链路。

用 multi-search-engine 做兜底 ​

另一个我觉得很适合做兜底的，是 multi-search-engine。

它的优点很明显：

  • 不依赖额外 API Key
  • 可以同时借助多个搜索引擎
  • 更适合当“补充方案”而不是唯一主搜索

比较合理的思路不是二选一，而是：

  • 主搜索优先 Tavily
  • 需要更多结果覆盖时，再让它使用 multi-search-engine
TOOLS.md
markdown
## Web Search
Use the openclaw-tavily-search skill as the top-priority search tool when do web search.
If the question requires searching for more relevant knowledge, ue multi-search-engine skill as an alternative solution.  // [!code ++]

这里面有个我自己很认同的方法论：

Skill 不是装得越多越好，而是要给每个 Skill 一个明确的定位。

主链路做什么，备选链路做什么，最好都写进 tools.md，否则能力越多反而越容易乱。

第四步：Skill 生态很强，但一定要带着“运维思维”去装 ​

如果按我自己的使用习惯来分，Skill 的来源大致就三类：

  • 内置 Skills
  • 官方 Skills 市场 Clawhub
  • GitHub 上的精选 Skill 仓库

这三类来源都能用，但真正决定你后面会不会踩坑的，不是“有没有地方下载”，而是你有没有把 Skill 当成一个需要审查、配置、验证的组件来看。

内置 Skill 适合低成本试用 ​

文中拿内置提醒类 Skill 做了例子，这类 Skill 的特点通常是：

  • 安装门槛低
  • 场景明确
  • 很适合快速验证“装完就能用”的能力

这类 Skill 非常适合做第一批试验。

官方市场适合找主力能力，但别无脑自动装 ​

这里有个提醒我自己也很认同： 市场里的 Skill 很多，但质量参差不齐，甚至不排除有风险实现。

所以更稳的做法是：

  • 优先看 star、活跃度和用途是否清晰
  • 尽量先人工审核，再决定要不要装
  • 不要让“自动找 Skill 并自动安装”的能力无限制运行

这也是为什么我现在对 Skill 的态度会更保守一些。因为一旦你开始把 OpenClaw 接到真实工作流里，Skill 就不再只是“玩具插件”，而是具备执行能力的外部组件。

精选仓库适合找方向，官方市场适合做安装入口 ​

另外还提到 GitHub 上有专门收集 OpenClaw Skills 的精选项目，我自己也更喜欢这种用法：

  • 先在精选仓库里按分类找方向
  • 看清楚这个 Skill 大概解决什么问题
  • 再回到官方市场里搜索具体条目并安装

先在外面找方向、再回市场里精确安装，这样思路更清楚，也不容易一头扎进市场里盲翻。

第五步：装 Skill 不是结束，真正的工作是配置环境变量和使用规则 ​

summarize 这个 Skill 是个很好的例子，我觉得它特别适合拿来提醒自己不要把“安装成功”误认为“能力已经可用”。

它能总结网页、PDF、图像，看起来很简单，但真正装起来时，流程其实是这样的：

  1. 找到 Skill 并安装
  2. 提供它依赖的 API Key
  3. 让 OpenClaw 把 Key 写进环境变量
  4. 按提示重启
  5. 再拿真实材料测试一次

也就是说，很多 Skill 并不是“装完就有完整能力”，而是“安装 + 注入配置 + 重启 + 验证”这一整套动作。

所以如果你后面想让 OpenClaw 稳定地接各种外部能力，建议始终记住这四个检查点：

  • 它有没有装上
  • 它依赖的 Key 有没有配好
  • 它有没有被写进正确的环境变量
  • 它在真实任务里有没有跑通

只检查第一项，往往远远不够。

第六步：先接飞书，而不是一上来就碰最复杂的渠道 ​

如果是我自己给别人排接入顺序，我也会先讲 飞书。

因为在现有生态里，飞书已经属于 OpenClaw 相对成熟、链路也比较清晰的聊天接入方案。它适合做第一条真正的“外部工作入口”。

按我自己的理解，飞书接入大致分成两半：

OpenClaw 侧：完成渠道配置 ​

这边的核心事情包括：

  • 安装对应插件
  • 在渠道配置里填入 App ID 和 App Secret
  • 选择合适的连接方式
  • 决定是否允许它在群里发言

飞书开放平台侧：把应用能力补完整 ​

这边主要是：

  • 创建企业自建应用
  • 配置权限
  • 开启机器人能力
  • 打开事件订阅
  • 添加“接收消息”事件
  • 创建版本并发布

这套流程看起来繁琐，但我看完以后反而更确定了一件事： 如果你想把 OpenClaw 从“本机工具”升级成“随时能在手机上对话的助理”，那飞书通常是最顺手的第一步。

此外还有一个非常实用的注意点： 在配置事件订阅时，OpenClaw 对应的进程最好保持运行状态，否则某些平台侧保存动作可能直接失败。

第七步：心跳机制，才是它开始“主动工作”的分水岭 ​

对很多人来说，真正让 OpenClaw 从聊天机器人变成代理系统的，不是接入飞书，而是心跳机制。

因为飞书接入解决的是“你能随时找它”，而心跳机制解决的是“它能不能主动找你”。

我对心跳机制这段印象很深，因为它把这件事讲得很清楚： 它会按固定间隔运行，每次运行时先读取 heartbeat.md，然后按里面的规则去检查，有结果就推送，没有结果就安静跳过。

心跳和定时任务，不是一回事 ​

心跳和定时任务的区别，我觉得一定要尽早分清。

心跳更适合：

  • 持续监控
  • 需要上下文的检查
  • 跟用户历史对话强相关的任务

定时任务更适合：

  • 某个固定时间点执行
  • 很明确的小动作
  • 不依赖完整对话历史的任务

可以粗暴一点理解：

  • 心跳 更像“定时巡逻”
  • 定时任务 更像“准点执行”

我觉得最典型的案例：每小时检查金价 ​

这里演示的是让它每小时检查一次金价，并主动发到飞书。我之所以觉得这个案例好，不是因为“查金价”本身，而是因为它刚好把心跳机制讲透了。

这个案例很典型，因为它刚好体现了心跳的两层结构：

  1. openclaw.json 决定运行间隔、渠道和发送目标
  2. HEARTBEAT.md 决定每次具体做什么

所以后面你如果想做类似的事情，比如：

  • 每小时检查某个服务是否正常
  • 每天巡检某个站点状态
  • 监控价格、汇率、库存、日志异常

都可以沿着这个结构去拆：

  • 配置负责调度
  • HEARTBEAT.md 负责逻辑

第八步：多 Agent 才是“一个 OpenClaw 变成一个团队”的开始 ​

如果说前面几段是在补能力，那后面真正把我思路拉开的部分，在我看来就是多 Agent。

这个能力的价值在于：你终于不用把所有人格、所有工具、所有记忆都塞到一个机器人里。

多 Agent 的本质：多个独立 workspace ​

这里其实可以理解得很直白： 一个 Agent，本质上就是一个独立机器人。

每个机器人都可以拥有：

  • 自己的人设
  • 自己的工具偏好
  • 自己的记忆
  • 自己的聊天渠道绑定

而这些差异，最终都会落到各自的 workspace 上。

这就意味着，多 Agent 真正解决的不是“多开几个聊天窗口”，而是：

  • 任务隔离
  • 角色隔离
  • 记忆隔离
  • 渠道隔离

为什么这个能力特别重要 ​

一旦你开始长期使用 OpenClaw，很容易出现一种混乱：

  • 一个机器人既要帮你查资料
  • 又要负责提醒
  • 还要扮演某种固定角色
  • 同时又接了多个渠道

最后的结果往往是它越来越难调，记忆越来越杂，行为越来越不稳定。

多 Agent 刚好可以把这些问题拆开。

比如你完全可以这样规划：

  • 一个 Agent 做日常通用助理
  • 一个 Agent 专门做飞书通知和巡检
  • 一个 Agent 专门做某种角色扮演或陪伴型对话
  • 一个 Agent 专门跑特定项目的工作流

用“林黛玉”式角色做示范，我觉得本质上展示的就是这件事： 你可以在同一套 OpenClaw 里，跑出多个性格、多个能力边界完全不同的机器人。

最后给一个更适合实操的升级顺序 ​

如果是我自己从零再来一遍，我会按下面这个顺序一步步升级，而不是一次性把所有高级功能全开：

  1. 先确认基础对话正常
  2. 先把默认工具权限放开
  3. 花时间把 workspace 里的关键文件读一遍
  4. 先修搜索，至少补上一个可用的主搜索 Skill
  5. 再补一个备选搜索 Skill
  6. 再开始装真正会进入工作流的 Skill，比如总结、提醒、搜索、外部系统接入
  7. 先接飞书，验证远程对话和通知链路
  8. 再上心跳机制，把“主动工作”跑起来
  9. 再拆多 Agent，把角色和任务分层
  10. 最后再把整套系统迁到云服务器

这个顺序的好处也很现实：

  • 每一步都能单独验证
  • 出问题时定位更简单
  • 不会在早期把本地、云端、渠道、自动化、多 Agent 全缠在一起

写在最后 ​

如果让我用一句话概括我自己的感受，那就是：

OpenClaw 的高级玩法，不是“会不会装更多东西”，而是你能不能把它从一个会聊天的模型壳，逐步改造成一个有权限、有记忆、有工具、有渠道、有主动性、还能分角色运行的长期代理系统。

如果你只是想“试试玩”，那基础安装就够了。 但如果你想让它真的进入日常工作流，那我觉得这几条主线基本都绕不过去：

  • 工作模式和工具权限
  • workspace 与记忆体系
  • 搜索能力重构
  • Skill 的筛选与治理
  • 通讯渠道接入
  • 心跳机制
  • 多 Agent
  • 云服务器与企业微信

把这几步真正走通以后，OpenClaw 才会从“能聊”变成“能干活”。
